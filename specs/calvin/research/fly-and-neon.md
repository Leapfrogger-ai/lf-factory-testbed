# Fly.io + Neon hosting for calvin

## Question

How should calvin run as one always-on Fly.io Machine (Hono web app plus a Temporal worker in the same process) backed by Neon Postgres on the free tier? What does each platform give us natively, what are the limits, and what does it cost per month against a ~$20 budget?

## Answer in one sentence

Run one `shared-cpu-1x` 512MB Machine in `sjc` with `auto_stop_machines = "off"` (about $4.40/month; Fly has no free tier for new orgs) and connect over TCP with `pg` to a free Neon project in `aws-us-west-2`, accepting Neon's 5-minute scale-to-zero, which can't be disabled on Free and adds a few hundred ms to the first query after idle.

## Versions / plans checked (2026-10-27)

- Fly.io docs at docs.fly.io (fly.io/docs/* now 301-redirects there) and the fly.io/pricing page, both read 2026-10-27.
- Neon docs at neon.com/docs, read 2026-10-27. Plans: Free and Launch (the cheapest paid plan).
- npm registry metadata, read 2026-10-27: `pg` 8.23.1 (engines `node >= 16.0.0`) and `@neondatabase/serverless` 1.2.0 (engines `node >=19.0.0`). The npmjs.com web pages returned 403, so these facts come from registry.npmjs.org/<pkg>/latest.

## Fly.io

### Autostop/autostart (`auto_stop_machines`, `auto_start_machines`, `min_machines_running`)

- **What it is:** Fly Proxy settings under `[http_service]` that stop or suspend idle Machines and start them again when requests arrive.
- **What it replaces:** Hand-rolled scale-to-zero, or leaving everything running.
- **Limits and behavior:**
  - The stop decision is based on traffic only. On a single Machine, "if the Machine has no traffic (a load of 0), then the proxy stops or suspends the Machine."
  - The docs don't say that background work or outbound connections keep a Machine alive. calvin's Temporal worker long-polls outbound, so with autostop on, the Machine (and the worker) would stop whenever there's no HTTP traffic. **Autostop must be off.**
  - Defaults when unset: `auto_stop_machines` is `"off"`, `auto_start_machines` is `true`, and `min_machines_running` is `0`. A `fly.toml` generated by `fly launch` may set these differently, so set them explicitly.
  - `min_machines_running` "only applies to your app's primary region" and has no effect unless autostop is `stop` or `suspend`.
- **Sources:**
  - https://docs.fly.io/launch/autostop-autostart: "If `"off"`, Fly Proxy will never stop Machines." It says to keep all Machines running by setting `auto_stop_machines` to `"off"` and `auto_start_machines` to `false`.
  - https://docs.fly.io/reference/fly-proxy-autostop-autostart: "if the Machine has no traffic (a load of 0), then the proxy stops or suspends the Machine."
  - https://docs.fly.io/reference/configuration: `auto_stop_machines`: "The default if not set is `"off"`." `min_machines_running`: "The default if not set is `0`."

### Process groups (`[processes]`)

- **What it is:** "Process groups are a way to configure a single Fly App to run multiple different programs."
- **What it replaces:** Running several programs inside one Machine with a supervisor.
- **Limits and trade-offs:**
  - Each group gets its own Machine(s): "Every defined process runs in its own Fly Machine(s) within the app, which means they don't compete for resources, and they can be scaled by process group."
  - So separate `web` and `worker` groups means at least two Machines and roughly twice the compute cost.
  - The docs give no guidance on running several programs in one Machine. Running web and worker in one Node process is just one process group (the default `app`), which is how calvin is planned.
  - Trade-off, as our inference: one process is cheaper and simpler, but a worker crash or CPU spike also affects page serving, and the two can't be scaled independently.
- **Sources:**
  - https://docs.fly.io/launch/processes: "Every defined process runs in its own Fly Machine(s) within the app, which means they don't compete for resources, and they can be scaled by process group."

### Secrets (`fly secrets`)

- **What it is:** Values stored in an encrypted per-app vault and exposed to Machines as environment variables.
- **What it replaces:** `.env` files or `[env]` in `fly.toml`. Use `[env]` only for non-secret config; it's committed with the repo.
- **Limits and behavior:**
  - `fly secrets set` restarts every Machine, which resets the ephemeral filesystem.
  - `--stage` stores the value without applying it. Apply staged values with `fly secrets deploy` or the next `fly deploy`.
- **Sources:**
  - https://docs.fly.io/apps/secrets: `fly secrets set` "sets one or more app secrets, then updates each Machine belonging to that Fly App."
  - Same page: "An app's secrets are available as environment variables at runtime on every Machine belonging to that Fly App."
  - Same page, on staging: "the staged secret will be available only on Machines that are started or updated after the `fly secrets set` command was run."
  - Same page, on restarts: setting a secret "involves a restart of the Machine and a consequent reset of its ephemeral file system."

### Health checks, deploy strategy, and `release_command`

- **What it is:**
  - `[[http_service.checks]]` defines HTTP checks with `grace_period`, `interval`, `timeout`, `method`, and `path`. These gate routing and deploys.
  - Top-level `[checks]` defines checks that don't affect routing.
  - `[deploy] strategy` controls how new versions roll out.
  - `[deploy] release_command` runs a one-off task, such as migrations, in a temporary Machine before the deploy.
- **What it replaces:** Running migrations by hand or at app boot, and an external uptime pinger for deploy gating.
- **Limits and behavior:**
  - The default strategy is `rolling`. `immediate` skips health checks. `bluegreen` needs at least one health check. `canary` can't be used with volumes.
  - On a single Machine, `rolling` replaces it in place, so expect a brief gap. `bluegreen` avoids that by booting a second Machine temporarily.
  - `release_command` has the app's env and secrets but no volumes. If it fails, the deploy stops.
- **Sources:**
  - https://docs.fly.io/reference/configuration: "The `release_command` lets you run a one-off task, like a database migration, before any of your deployed Machines are created or updated."
  - Same page, on failure: "If the command fails, the deploy will stop."
  - Same page, on access: the temporary Machine has "full access to the network, environment variables and secrets, but *not* to persistent volumes."
  - Same page, on `immediate`: "Replace all Machines with new releases immediately without waiting for health checks to pass."
  - Same page, on `bluegreen`: "You need to configure at least one health check to use the `bluegreen` strategy."
  - Same page, on top-level checks: use `[checks]` "instead of `[[services.checks]]`" when you want health checks that don't affect request routing.

### Regions and Machine pricing (`primary_region`, Started Machines)

- **What it is:**
  - `primary_region = "sjc"` (San Jose) decides where `fly deploy` creates Machines.
  - Machine prices vary by region using a multiplier on the Ashburn price. `sjc` is 1.192.
- **What it replaces:** Choosing and paying for a VPS.
- **Limits and pricing:**
  - `shared-cpu-1x` 256MB costs $2.19/month in iad and $2.62/month in sjc.
  - `shared-cpu-1x` 512MB costs $3.69/month in iad, so about $4.40/month in sjc. That's our calculation: 3.69 × 1.192.
  - `shared-cpu-1x` 1GB costs $6.70/month in iad, so about $7.99/month in sjc.
  - A stopped Machine is billed only for rootfs, at $0.15/GB/month.
  - Shared IPv4 and Anycast IPv6 are free. Dedicated IPv4 costs $2/month.
  - North America egress is $0.02/GB. Inbound is free.
  - There's no platform fee.
  - **No free tier for new orgs.** The trial covers 2 hours of Machine runtime or 7 days, whichever comes first. Legacy (pre-Oct-2024) orgs keep their old allowances.
- **Sources:**
  - https://docs.fly.io/about/pricing: "Machine prices in this table are for Ashburn, Virginia (`iad`) and Secaucus, NJ (`ewr`), our lowest-priced regions."
  - Same page: a `shared-cpu-1x` "Machine with 512MB costs $3.69 per month when running continuously."
  - Same page: "New organizations don't have a free tier or a monthly free usage allowance."
  - Same page, on the trial: it covers "up to 2 hours of Machine runtime or 7 days, whichever comes first."
  - Same page: "Organizations on plans discontinued in October 2024 keep the free allowances included with those plans."
  - Same page, on addresses: "Each application receives a shared IPv4 address and unlimited Anycast IPv6 addresses for global load balancing."
  - Same page, on egress: "$0.02/GB in North America and Europe."
  - https://fly.io/pricing/, the `sjc` row: "| San Jose, California (US) | sjc | 1.192 | $2.62 | $39.35 |"
  - Same page: "A region's price is the Ashburn price above times its multiplier, applied to vCPU and RAM."
  - https://docs.fly.io/reference/regions: "| sjc | San Jose, California (US) | ✓ | ✓ |"
  - https://docs.fly.io/reference/configuration: `fly deploy` uses `primary_region` "to determine where to create new Machines."

### Custom domains and TLS (`fly certs`)

- **What it is:**
  - Every app gets HTTPS on `<app>.fly.dev`.
  - `fly certs add <domain>` issues a Let's Encrypt certificate that renews automatically.
  - `force_https` redirects HTTP to HTTPS.
- **What it replaces:** Managing certificates yourself, or a CDN in front of the app.
- **Limits and pricing:**
  - Use A/AAAA records for an apex domain and a CNAME to `<app>.fly.dev` for subdomains.
  - The first 10 single-hostname certificates are free. After that it's $0.10/month per hostname, or $1/month per wildcard.
- **Sources:**
  - https://docs.fly.io/networking/custom-domain: "Use A and AAAA records for most direct connections to your app."
  - Same page: custom domains can "have HTTPS set up for you as it is with your `.fly.dev` domain."
  - https://docs.fly.io/about/pricing: certificates cost "$0.10/month per single hostname" and "$1/month per wildcard," with the first 10 single-hostname certificates free.
  - https://docs.fly.io/reference/configuration, on `force_https`: "A Boolean which determines whether to enforce HTTP to HTTPS redirects."

### Logging (`fly logs`, log search, Log Shipper)

- **What it is:** The Machine's init process captures stdout and ships it through Vector and NATS. You can live-tail it with `fly logs` or the dashboard, and search it in the Grafana-based log search.
- **What it replaces:** A logging SaaS, at PoC scale.
- **Limits:**
  - Log search keeps 7 days.
  - The docs give no other retention period.
  - For longer retention, export with the Fly Log Shipper app or the Logs API.
- **Sources:**
  - https://docs.fly.io/monitoring/logging-overview: "The init program is, among other things, gathering process output from stdout and redirects it to a socket."
  - Same page: you can live tail logs "with the `fly logs` command."
  - Same page, on log search: it "retains logs for 7 days."

## Neon

### Plans (Free, Launch)

- **What it is:** Managed serverless Postgres.
- **What it replaces:** A self-run Postgres or Fly's paid Managed Postgres.
- **Free plan limits:**
  - 100 CU-hours per project per month.
  - 1 GB storage per project, 20 GB per account.
  - 10 branches per project.
  - 5 GB egress per project.
  - Computes up to 2 CU.
  - Scale to zero after 5 minutes, and it can't be disabled.
  - 6-hour restore window.
- **Launch plan:**
  - Pay-as-you-go: $0.106 per CU-hour and $0.35 per GB-month, with no minimum fee.
  - Scale to zero can be disabled.
- **Cost of always-on (our arithmetic):** At the 0.25 CU minimum running 730 hours, that's about 182 CU-hours.
  - On Launch, that comes to about $19.35/month. That breaks a $20 total budget.
  - On Free, it's more than the 100 CU-hour allowance, so a keep-alive ping is not viable either.
- **Sources:**
  - https://neon.com/docs/introduction/plans: "100 CU-hours/project"
  - Same page: "1 GB/project, 20 GB account total"
  - Same page: "5 min inactivity; cannot disable"
  - Same page: "6 hours, up to 1 GB-month"
  - Same page: "5 GB per project included"
  - Same page, Launch pricing: "$0.106/CU-hour" and "$0.35/GB-month"

### Scale to zero

- **What it is:** The compute suspends after 5 minutes without activity and resumes when the next connection or query arrives.
- **What it replaces:** Paying for an idle database.
- **Limits:**
  - Resuming takes "a few hundred milliseconds" plus network time.
  - On Free you have to live with it. Use connection timeouts of several seconds and retry with backoff.
  - On paid plans it can be turned off.
- **Sources:**
  - https://neon.com/docs/introduction/scale-to-zero: Neon "automatically scales to zero after 5 minutes."
  - Same page, on resuming: the database "reactivates automatically within a few hundred milliseconds."
  - Same page, on paid plans: "Paid plan users can disable the scale-to-zero setting to maintain an always-active compute."
  - https://neon.com/docs/connect/connection-latency: "activating a Neon compute from an idle state typically takes a few hundred milliseconds."
  - Same page: "By configuring longer connection timeout durations, your application has more time to accommodate cold starts."

### Connection pooling (pooled vs direct connection strings)

- **What it is:**
  - The pooled string uses a `-pooler` hostname, served by PgBouncer in transaction mode with up to 10,000 client connections.
  - The direct string connects straight to Postgres.
- **What it replaces:** Running your own PgBouncer.
- **Limits:**
  - Pooled connections don't support SET/RESET, LISTEN/NOTIFY, SQL-level PREPARE, session advisory locks, or WITH HOLD cursors.
  - Protocol-level prepared statements are supported.
  - Use direct connections for migrations and pg_dump.
  - Don't double-pool: a client-side pool on top of the Neon pooler is discouraged.
- **Guidance for calvin:** For one long-running Node process with a small `pg.Pool`, either string works.
  - Neon's default advice is pooled.
  - Its "avoid client-side pooling on top" advice points to the direct string plus a small `pg.Pool`, given we have one host and low volume.
  - Run migrations through `release_command` on the direct string either way.
- **Sources:**
  - https://neon.com/docs/connect/connection-pooling: Neon runs PgBouncer in "transaction mode."
  - Same page, on prepared statements: "PgBouncer supports protocol-level prepared statements (as of PgBouncer 1.22.0)."
  - https://neon.com/docs/connect/choose-connection: "Use pooled connections by default."
  - Same page, on double pooling: if you use a pooled Neon connection, "avoid adding client-side pooling on top."

### Drivers (`pg` vs `@neondatabase/serverless`)

- **What it is:**
  - `pg` (node-postgres 8.23.1) is a standard TCP client with `Pool`.
  - `@neondatabase/serverless` (1.2.0, needs Node ≥19) is "node-postgres for serverless environments" and connects over HTTP or WebSocket.
- **Guidance:** For a VM or container host like a Fly Machine, Neon recommends a TCP driver: `pg`, postgres.js, or Bun.SQL.
- **Sources:**
  - https://neon.com/docs/connect/choose-connection: "use a standard TCP driver with connection pooling."
  - Same page: "Your server can maintain a connection pool across requests, making TCP the fastest and most efficient option."
  - Same page, on the serverless driver: it "connects over HTTP or WebSockets instead of TCP, reducing connection setup latency."
  - registry.npmjs.org: `pg` is at 8.23.1, described as "PostgreSQL client - pure javascript & libpq with the same API," with engines `node >= 16.0.0`.
  - registry.npmjs.org: `@neondatabase/serverless` is at 1.2.0, described as "node-postgres for serverless environments from neon.com," with engines `node >=19.0.0`.

### Regions

- **What it is:** A project's region is fixed when you create it.
- **Options near sjc:** The closest is AWS US West (Oregon), `aws-us-west-2`. There is no California region. Azure regions are deprecated for new projects.
- **Latency:**
  - The docs give no sjc-to-Oregon figure. Expect a cross-region round trip on every query; we haven't measured it.
  - Implication: keep queries per page few. Ideally one or two round trips per render, so the ≤2s 4G budget is dominated by the client network, not the database.
- **Sources:**
  - https://neon.com/docs/introduction/regions: lists "AWS US West (Oregon): `aws-us-west-2`."
  - Same page, on choosing: "choose the region closest to your application server."
  - Same page, on changing: you "cannot change the region" for an existing project.

### Branching and instant restore

- **What it is:** Instant copy-on-write branches, used for dev and test databases. Instant restore rolls a branch back to any point inside the history window.
- **What it replaces:** Dump/restore to seed dev databases, and backups at PoC scale.
- **Limits:**
  - Free allows 10 branches per project.
  - The history window is 6 hours on Free and 1 day on paid plans. It can be extended to 7 days on Launch.
- **Sources:**
  - https://neon.com/docs/introduction/branching: "A branch is a copy-on-write clone of your data."
  - Same page, on speed: "Neon branching creates copy-on-write clones of your database instantly."
  - Same page, on restore: you can "roll the branch back to any point in time that still falls within your project's history window."

### Connection string secret (`DATABASE_URL`)

- **What it is:** Neon gives a full `postgresql://…?sslmode=require` URL, available as pooled or direct. Its Node guide uses discrete `PG*` env vars instead.
- **How to store it:** Run `fly secrets set DATABASE_URL=...` so the app reads it from `process.env.DATABASE_URL`. Optionally set `DATABASE_URL_DIRECT` as a second secret for migrations.
- **Sources:**
  - https://neon.com/docs/connect/connection-pooling: "postgresql://user1:AbC123dEf@ep-cool-darkness-123456-pooler.us-east-2.aws.neon.tech/dbname?sslmode=require"
  - https://docs.fly.io/apps/secrets: "An app's secrets are available as environment variables at runtime on every Machine belonging to that Fly App."

## Implications for calvin

- **Keep the Machine on.** In `fly.toml`, set `primary_region = "sjc"` and, under `[http_service]`, set `auto_stop_machines = "off"`, `auto_start_machines = false`, and `force_https = true`. Fly's autostop looks only at proxy traffic, so with it on, the Temporal worker would be stopped whenever the site is idle.
- **One process group, one Machine.** Web plus worker in one Node process fits the single-Machine budget. Separate `[processes]` groups would double compute. Accept the shared-fate risk and add a health check (`[[http_service.checks]]` on e.g. `/healthz`).
- **Machine size:** `shared-cpu-1x` with 512MB in sjc, about $4.40/month. 256MB ($2.62) is likely tight for Node plus the Temporal SDK worker; that's our judgment, not documented.
- **Migrations:** Run them via `[deploy] release_command` using the direct Neon string. A failed migration aborts the deploy.
- **Deploy gap:** The default `rolling` strategy on one Machine gives a brief gap during deploys. Use `bluegreen` (needs a health check) if that matters.
- **Database:**
  - Use Neon Free in `aws-us-west-2` with the `pg` driver (not `@neondatabase/serverless`) and a small `pg.Pool`.
  - Accept scale-to-zero: the first request after 5 idle minutes pays a few hundred ms resume plus the Oregon round trip.
  - Set `connectionTimeoutMillis` to several seconds and retry once.
  - Keep the public page to one or two queries.
- **Polling:** Don't poll the database from the worker on a timer. It would keep Neon awake and burn the 100 CU-hour Free allowance (always-on 0.25 CU is about 182 CU-hours/month).
- **Secrets:**
  - Set `DATABASE_URL` (plus `DATABASE_URL_DIRECT`), the Temporal Cloud credentials, and any API keys with `fly secrets set`.
  - Use `--stage` to batch them before the first deploy.
  - Nothing secret goes in `fly.toml`.
- **TLS and domain:** HTTPS is free on `*.fly.dev` and on up to 10 custom hostnames via `fly certs add`. The shared IPv4 is free, so no dedicated IPv4 is needed.
- **Logs:** stdout goes to `fly logs`, and log search keeps 7 days. That's enough for a PoC; add the Log Shipper only if longer retention is needed.
- **Estimated monthly cost:**
  - Fly Machine (`shared-cpu-1x` 512MB, sjc, always on): about $4.40.
  - Egress: under $0.10 at this volume.
  - Certificates and shared IPv4: $0.
  - Neon Free: $0.
  - **Total about $4.50/month**, leaving roughly $15 of headroom (for example, for Temporal Cloud, which is out of scope here).
  - Switching to Neon Launch with always-on compute would add about $19.35 and blow the budget, so stay on Free.
