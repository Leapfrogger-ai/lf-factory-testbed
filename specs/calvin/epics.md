# Epics: calvin

Maturity: **poc**. Stories use the terms in the glossary (plan, creator, commit, committer, withdraw, minimum, count, commit deadline, confirmed, called off, gathering, check-in). Every criterion is checked by a test at a seam the test strategy names, unless it says "checked by hand". In that case the story's plan records how it was checked. Test command `npx vitest run`, type check `npx tsc --noEmit`, and the setup command is the one in the factory config.

Every time is in `America/Los_Angeles`. The example plan used throughout is coffee at Blue Bottle, Oakland (rough area "Rockridge", rough time "next weekend, morning"), on Sat 14 Nov 2026 at 10:00 AM PST (`2026-11-14T18:00:00Z`), minimum 3, created by Ana Ruiz and published at Mon 9 Nov 2026 10:00 AM, so its commit deadline is Wed 11 Nov 2026 10:00 PM (`2026-11-12T06:00:00Z`).

**Decided in this stage: the default commit deadline floors at halfway.** FR007's default was the earlier of 48h before the gathering and halfway between publishing and the gathering. For a gathering less than 48h away, that default is in the past, and publishing would be refused. The operator's decision: use the earlier of the two when it's in the future, otherwise use halfway. The rule is still rounded down to the whole minute. PRD FR007 and the API specification's R3 deadline rule are updated to match.

## Epic 1: Create and publish a plan

A creator turns a city, a rough area and a rough time into a published plan, with a public link to paste in the chat and a manage link emailed to them. It covers FR001–FR010, NFR001, NFR003, NFR005 and NFR009.

Greenfield: the repo holds only specs, so this epic starts with the starter code and the guardrails stories.

### Story 1.1 (v1): Project skeleton

As the team, we want the calvin stack running with its test runner and CI, so that every later story lands on a working build.

The stack is the one the architecture's Project Initialization section lists: Node 26 running TypeScript directly with no build step, Hono with `@hono/node-server`, zod, Drizzle 0.45.4 with `pg`, and Vitest 5, with every `@temporalio/*` package pinned to exactly 1.24.0. The app is built by `createApp(deps)`, with `deps = { db, now, suggestPlanCall, sendEmail, planWorkflows }`. Only the entry point builds the real ones. The Vitest config does what the test strategy's Commands section says: a global setup that creates the worktree's database (`FACTORY_DB_NAME`) if it's missing and applies every migration, `fileParallelism: false`, `TEST_DATABASE_URL` built in the config, and `testTimeout: 30_000`. The first migration is the database schema's Migration 0000, generated by drizzle-kit from the Drizzle schema. The story also adds the shared test fakes and helpers the test strategy lists (`fakeEmail`, `fakePlanWorkflows`, `fakeSuggest`, `fixedClock`, `testDeps`, `testDb`, `resetDb`), the JSON-lines logger, the request logger with token redaction, the not-found page and `app.onError`, and the response headers from the API specification's §2. Environment variables are read and validated with zod in one config module. The entry point starts the HTTP server and a Temporal worker on task queue `calvin`. If the worker can't run on Node 26, fall back to Node 24 with `temporal-polyfill` 1.0.x, as the architecture's Node risk says.

Prerequisites: None

Acceptance criteria:
- Given a fresh clone, when I run the setup command and then `npx vitest run`, then the suite passes.
- Given a fresh clone after setup, when I run `npx tsc --noEmit`, then it exits with code 0.
- Given no worktree database exists yet, when `npx vitest run` starts, then the database is created and every migration is applied, so the six tables in the database schema (`suggestions`, `plans`, `commits`, `email_sends`, `check_in_answers`, `events`) exist.
- Given a pull request to `main`, when CI runs, then the `ci` job runs `npx vitest run` on `ubuntu-latest` with Node 26 and a `postgres:17` service on `54329:5432`, and reports the result on the pull request.
- Given the app, when `GET /healthz` is requested, then it answers 200 with `text/plain` body `ok` and doesn't query the database.
- Given the app, when an unknown path such as `GET /nope` is requested, then it answers 404 with the page "We can't find that plan. The link may be incomplete. Check it in your chat or email." and a "Suggest a plan" link to `/`.
- Given the not-found page, when its response headers are read, then they include `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Robots-Tag: noindex` and the Content-Security-Policy from the API specification's §2.
- Given a request to `/p/` followed by a 43-character token, when the request is logged, then the log line shows the path as `/p/:token` and doesn't contain the token.
- Given a required environment variable such as `DATABASE_URL` is unset, when the app starts, then it exits with an error that names the variable and prints no secret value (checked by hand).
- Given a local `temporal server start-dev`, when the app starts on Node 26, then the HTTP server answers on port 8080 and the worker polls task queue `calvin` (checked by hand).

### Story 1.2 (v1): Guardrails

As the team, we want the coding standards' mechanical rules checked in CI, so that reviewers only judge what tools can't.

The mechanical rules are types (TypeScript with `"strict": true`, `"erasableSyntaxOnly": true`, `"verbatimModuleSyntax": true`, `"allowImportingTsExtensions": true`, `"noEmit": true`), passing tests, and no committed secret (the gitleaks CLI with its default rules and `--redact`, not gitleaks-action). There's no formatter and no linter at poc. The `ci` job's steps become: checkout with full history (`fetch-depth: 0`), `gitleaks git --redact --exit-code 1`, `npm ci`, `npx tsc --noEmit`, `npx vitest run`, with `FACTORY_DB_NAME=calvin_test` and no secrets set. Making `ci` a required status check on `main` is a GitHub setting. The plan says how the operator turns it on.

Prerequisites: Story 1.1

Acceptance criteria:
- Given a change with a type error, when CI runs, then `npx tsc --noEmit` fails and the merge is blocked.
- Given a change that declares a TypeScript `enum`, when CI runs, then the type check fails under `erasableSyntaxOnly` and the merge is blocked.
- Given a change with a failing test, when CI runs, then `npx vitest run` fails and the merge is blocked.
- Given a commit that adds a secret, such as an API key in source, when CI runs, then `gitleaks git --redact --exit-code 1` fails over the pull request's commits, the log shows the secret redacted, and the merge is blocked.
- Given a clean pull request, when CI runs, then every step passes within 5 minutes.

### Story 1.3 (v1): Publish a plan from a filled-in form

As a creator, I want to fill in a plan and publish it, so that I get a link to paste into my group's chat.

Until Story 1.7 adds suggestions, `GET /` shows the plan form in the fallback shape (UX mockup 1c): city (from the configured `CITIES`, in the architecture's order, no default), rough area, rough time, then format, venue, date, time, minimum (default 3), Decide by (empty), "You're the first one in", your name, your email, and **Publish plan**. `POST /plans` (the API specification's R3) parses the gathering as wall-clock time in `America/Los_Angeles`, resolves the commit deadline, and computes the plan's schedule as UTC instants (24h reminder, 08:00 morning reminder or none, 10:00 check-in the next day) with the pure plan rules and the JS `Temporal` time helpers. It generates 256-bit tokens, then in one transaction inserts the plan, the creator's commit and the `plan.published` and `commit.added` events, and starts `planWorkflow` with ID `plan-<planId>` before the transaction commits. The real `planWorkflows` wraps the Temporal client, connected with `loadClientConnectConfig()`. The workflow has no timers yet; Epic 3 gives it them. The published screen (R4) shows the public link and a quiet **Manage your plan** link. The base stylesheet with the UX spec's §4 tokens, including dark mode, arrives with this first page.

Prerequisites: Story 1.1

Acceptance criteria:
- Given a valid form for coffee at Blue Bottle in Oakland on 2026-11-14 at 10:00 with minimum 3 and no Decide by, when it's published at Mon 9 Nov 2026 10:00 AM, then the response is 303 to `/m/<manageToken>/published`, and the plan's gathering is `2026-11-14T18:00:00Z` and its commit deadline is `2026-11-12T06:00:00Z` (halfway, which is earlier than 48h before).
- Given the same gathering and no Decide by, when it's published at Wed 11 Nov 2026 10:00 AM, then the commit deadline is `2026-11-12T18:00:00Z` (48h before the gathering, which is earlier than halfway).
- Given the same gathering and no Decide by, when it's published at Fri 13 Nov 2026 10:00 AM, then the commit deadline is `2026-11-14T06:00:00Z` (halfway, because 48h before is already past).
- Given a form with Decide by 2026-11-13 at 18:00, when it's published at Mon 9 Nov 2026 10:00 AM, then the commit deadline is `2026-11-14T02:00:00Z`.
- Given a published plan, when it's read back, then its state is open, the creator is its only committer with a count of 1, and the events `plan.published` and `commit.added` (with `change: "new"`, `isCreator: true`, `activeCount: 1`) are recorded.
- Given a published plan, when its public, manage and check-in tokens and the creator's withdraw token are read, then each is 43 characters from the base64url alphabet and all four differ.
- Given the example plan published at Mon 9 Nov 2026 10:00 AM, when it's published, then `planWorkflows.start` is called once with its plan ID and the schedule: deadline `2026-11-12T06:00:00Z`, 24h reminder `2026-11-13T18:00:00Z`, morning reminder `2026-11-14T16:00:00Z`, check-in `2026-11-15T18:00:00Z`.
- Given a gathering at 09:30 on 2026-11-14, when the schedule is computed, then it has no morning reminder.
- Given a gathering on Sun 1 Nov 2026 at 10:00 (the fall-back day), when the schedule is computed, then the 24h reminder is `2026-10-31T18:00:00Z`, the morning reminder `2026-11-01T16:00:00Z` and the check-in `2026-11-02T18:00:00Z`.
- Given a gathering on Sun 14 Mar 2027 at 10:00 (the spring-forward day), when the schedule is computed, then the 24h reminder is `2027-03-13T17:00:00Z`, the morning reminder `2027-03-14T15:00:00Z` and the check-in `2027-03-15T17:00:00Z`.
- Given `planWorkflows.start` fails, when a valid form is published, then the response is the 500 system-error page "Something went wrong. Go back and try again." with no stack trace, and no plan is stored.
- Given a published plan, when `GET /m/<manageToken>/published` is requested, then it shows "Your plan is ready to share", the public link `BASE_URL/p/<publicToken>`, and a "Manage your plan" link to `/m/<manageToken>`.
- Given a manage token that matches no plan, or a malformed one, when `GET /m/<token>/published` is requested, then it answers 404 with the not-found page, and the malformed one doesn't query the database.

### Story 1.4 (v1): Publishing refuses an invalid plan

As a creator, I want to be told exactly what's wrong when my plan can't be published, so that I can fix it without retyping anything.

Validation follows the API specification's R3 rules and §3.2 messages. Every error is collected and shown at once under its field, the page is re-rendered with 422, everything entered is kept, and nothing is stored. CSRF protection (`hono/csrf` with `origin: BASE_URL`) and the 16 KB body limit cover every POST from here on.

Prerequisites: Story 1.3

Acceptance criteria:
- Given a form with no city, an empty area and an empty rough time, when it's published, then the response is 422 with "Pick a city.", "Add a rough area." and "Add a rough time." under those fields, the other entered values kept, and no plan stored.
- Given a city that isn't in `CITIES`, when the form is published, then the response is 422 with "Pick a city.".
- Given an empty format and an empty venue, when the form is published, then the response is 422 with "Say what it is, like coffee or a walk." and "Add where it is.".
- Given a venue of 121 characters, when the form is published, then the response is 422 with "Keep it under 120 characters.".
- Given a missing or malformed date or time, when the form is published, then the response is 422 with "Pick a date." or "Pick a time.".
- Given a gathering that isn't in the future, when the form is published, then the response is 422 with "The gathering needs to be in the future.".
- Given a minimum of 1, or one that isn't a whole number, when the form is published, then the response is 422 with "The minimum is at least 2 people, you included.".
- Given a minimum of 40, when the form is published, then the plan is published with minimum 40.
- Given only one of Decide by's date and time, when the form is published, then the response is 422 with "Pick both a date and a time, or leave both empty.".
- Given a Decide by that isn't in the future, when the form is published, then the response is 422 with "The decide-by time needs to be in the future." under Decide by.
- Given a Decide by at or after the gathering, when the form is published, then the response is 422 with "The decide-by time needs to be before the gathering." under Decide by.
- Given an empty name and an email "ana@", when the form is published, then the response is 422 with "Add your name." and "That email doesn't look right.".
- Given a POST whose `Origin` isn't `BASE_URL` and whose `Sec-Fetch-Site` isn't `same-origin`, when it's sent to `/plans`, then the response is the 403 system-error page and nothing is stored.
- Given a POST body over 16 KB, when it's sent to `/plans`, then the response is the 413 system-error page.

### Story 1.5 (v1): Email the creator their manage link

As a creator, I want my private manage link emailed to me, so that I can find my plan again later.

This story builds the email path every later email uses. `sendEmail(payload, idempotencyKey)` wraps Resend's `emails.send` and turns its `{ data, error }` into a return value or a thrown error: retryable for `rate_limit_exceeded`, 409 `concurrent_idempotent_requests` and 5xx, and `ApplicationFailure.nonRetryable` for validation, auth and quota errors. `sendOnce(kind, plan, commit)` inserts the `email_sends` row with `ON CONFLICT DO NOTHING`, returns if it's already sent, sends with idempotency key `<kind>/<planId>/<commitId>` and tag `kind=<kind>`, then sets `sent_at` and appends `email.sent`. The payload is plain text, built only from stored data. The manage-link email follows the UX spec's §8.9 and is sent in the publish request, after the transaction. Verifying the sending domain in Resend (SPF and DKIM, NFR009) is an operator task, done before the trial.

Prerequisites: Story 1.3

Acceptance criteria:
- Given the example plan, when it's published, then `sendEmail` is called once to the creator's address with subject "Your plan: Coffee at Blue Bottle, Sat 14 Nov", a text body with the manage link `BASE_URL/m/<manageToken>` and the public link `BASE_URL/p/<publicToken>`, no withdraw link, tag `kind=manage_link`, and idempotency key `manage_link/<planId>/<creatorCommitId>`.
- Given the manage-link email was sent, when the published screen is shown, then it reads "We've emailed you a private link to manage the plan. Keep it to yourself.".
- Given `sendEmail` fails, when the plan is published, then the response is still 303 to the published screen, the failure is logged at `error` with no email address in the log line, and the screen reads "We couldn't email you your private link. Bookmark the link below to manage the plan.".
- Given `sendOnce` has already sent a kind to a committer, when it's called again for the same kind and committer, then `sendEmail` isn't called again, there's still one `email_sends` row, and one `email.sent` event.
- Given a first `sendOnce` call whose send failed, when it's called again, then `sendEmail` gets the same payload and the same idempotency key as the first call.
- Given Resend answers `rate_limit_exceeded` or a 5xx, when `sendEmail` runs, then it throws a retryable error, and given it answers a validation or auth error, then it throws a non-retryable one.

### Story 1.7 (v1): Get a suggestion

As a creator, I want calvin to suggest a concrete plan from my city, rough area and rough time, so that I have something specific to offer.

`GET /` now opens on the inputs state (UX mockup 1a): city, rough area, rough time and **Suggest a plan**. `POST /suggest` (the API specification's R2) validates, calls `suggest()`, stores one `suggestions` row (ok or failed, with `latency_ms` and the default commit deadline), and redirects 303 to `/?suggestion=<id>`. `GET /` renders the suggestion card (mockup 1b) or the fallback (mockup 1c) from that row, so a refresh never calls Claude again. `suggest()` follows ADR 0004 and the architecture's Anthropic configuration: `claude-sonnet-5-5`, `web_search_20260318` with `max_uses: 2` and an approximate `user_location` for the city, the strict client tool `propose_plan`, `effort: "low"`, `timeout: 20_000`, `maxRetries: 0` and an abort signal at 20s. The prompt asks for a low-stakes format (coffee, drinks, a walk), never hosting at someone's home. Publishing from the card carries `suggestionId`, follows R3's deadline rule 3, and records `suggestion_edited`. The good recorded response is captured once by hand from a real call, with anything personal removed. The others are edits of it. Real latency (NFR001, ≤ 15s p95) is measured by hand over at least 10 real calls. If it's over, `max_uses` drops to 1.

Prerequisites: Story 1.4

Acceptance criteria:
- Given Oakland, "Rockridge" and "next weekend, morning", when they're submitted to `POST /suggest` with the recorded good response, then the response is 303 to `/?suggestion=<id>`, and that page shows the summary "Oakland · Rockridge · next weekend, morning", a card with the proposal's format, venue, when, minimum and Decide by, and the publish form with your name and email.
- Given a suggestion request, when `suggestPlanCall` is called, then the request names model `claude-sonnet-5-5`, the `web_search_20260318` tool with `max_uses: 2` and `user_location` city "Oakland", region "California", country "US" and timezone "America/Los_Angeles", and the `propose_plan` tool with `strict: true`, and it sets no `temperature`, no `thinking: disabled` and no forced `tool_choice`.
- Given a response with no `propose_plan` call, or one that ends in `pause_turn`, `refusal` or `max_tokens`, or an API error, or no answer within 20 seconds, when the suggestion is requested, then the `suggestions` row is failed with the matching `failure_reason`, and the page shows "We couldn't come up with a suggestion just now. Fill in your own below, or try again." with empty format, venue, date, time and Decide by, minimum 3, and never a 5xx.
- Given a `propose_plan` call with minimum 1 or an empty venue, when the suggestion is requested, then the row is failed with reason `invalid_proposal` and the fallback is shown.
- Given empty inputs, when they're submitted to `POST /suggest`, then the response is 422 with "Pick a city.", "Add a rough area." and "Add a rough time." and Claude isn't called.
- Given a suggestion page, when it's requested a second time, then `suggestPlanCall` isn't called again.
- Given `GET /?suggestion=` with a value that isn't a UUID or matches no row, when it's requested, then it answers 200 with the plain inputs state.
- Given an ok suggestion published without changes, when the plan is read back, then its `suggestion_id` is that suggestion and `suggestion_edited` is false.
- Given an ok suggestion published with its venue changed, when the plan is read back, then `suggestion_edited` is true.
- Given an ok suggestion whose When is changed while Decide by is left at the suggestion's default, when it's published, then the commit deadline is the default for the new When, not the suggestion's.
- Given a plan published from the fallback form, when it's read back, then it has no `suggestion_id`.
- Given 10 real suggestion calls for different cities, when their `latency_ms` is read, then the p95 is at most 15 seconds (checked by hand).

### Story 1.9 (v1): Rate limits on suggesting and publishing

As the operator, I want suggesting and publishing capped per IP and per day, so that nobody can run up the Claude bill or email arbitrary addresses at scale.

The limits are the API specification's §4: fixed windows, in-memory counters, keyed by the `Fly-Client-IP` header (the socket address in development), a "day" being the calendar day in `America/Los_Angeles`, and the limits as constants in config. Every request that passes CSRF counts, checked before validation and before any Claude call or database write.

Prerequisites: Story 1.7

Acceptance criteria:
- Given 10 suggestion requests from one IP within 10 minutes, when an 11th arrives, then the response is 429 with a `Retry-After` header, the create page shows "Lots of suggestions just now. Fill in your own below, or try again in a few minutes." with the fallback card, Claude isn't called, and no `suggestions` row is stored.
- Given 200 suggestion requests on one Los Angeles calendar day from different IPs, when a 201st arrives, then it gets 429.
- Given 5 publish requests from one IP within an hour, when a 6th arrives, then the response is 429 with "Lots of plans from here just now. Try again in a little while.", everything entered kept, and no plan stored.
- Given 50 publish requests on one Los Angeles calendar day, when a 51st arrives, then it gets 429.
- Given one IP at its limit, when a request arrives from another IP, then it isn't limited.
- Given 10 invalid suggestion requests from one IP, when an 11th valid one arrives within 10 minutes, then it gets 429.
- Given a request is limited, when it's logged, then the line is at `warn` and doesn't contain the IP.

### Story 2.2 (v1): A plan is confirmed when it reaches its minimum

As a creator, I want the plan to be on as soon as enough people commit, so that everyone knows it's happening.

The commit that brings the count to the minimum before the commit deadline confirms the plan in the same transaction (FR018) and records `plan.confirmed`. After the transaction, the route signals the plan's workflow. Signals are fire-and-forget: a failure is logged at `error` and the commit stands (ADR 0002). Commits stay open on a confirmed plan until the gathering starts (FR014). The confirmation email itself is Story 3.2.

Prerequisites: Story 2.1

Acceptance criteria:
- Given the example plan with Ana and Raj in before its deadline, when Mia commits, then the plan is confirmed, a `plan.confirmed` event is recorded, the response redirects with `notice=on`, the page shows "You're in, Mia. It's on! We've emailed you the details and we'll remind you the day before.", and `planWorkflows.signal` is called once with `confirmed`.
- Given a confirmed plan before its gathering, when its public page is requested, then the pill reads "It's on", every seat is filled with no empty seats, the page reads "More people are welcome until it starts.", the form is shown, and `og:description` ends with " It's on.".
- Given a confirmed plan after its commit deadline and before its gathering, when a new person commits, then the commit is stored, the response redirects with `notice=on`, and `planWorkflows.signal` is called with `committed` and the new commit's ID.
- Given a confirmed plan, when an existing committer commits again, then no signal is sent.
- Given `planWorkflows.signal` fails, when the confirming commit is submitted, then the plan is still confirmed, the response is the usual 303, and the failure is logged at `error`.
- Given a plan one commit short of its minimum, when two people commit at the same time, then the plan is confirmed once, with one `plan.confirmed` event and one `confirmed` signal.
- Given a confirmed plan whose gathering started less than 3 hours ago, when its public page is requested, then the pill reads "Happening now" and there's no form.
- Given a confirmed plan whose gathering started 3 hours ago or more, when its public page is requested, then the pill reads "This was on Sat 14 Nov" and there's no form.

### Story 2.3 (v1): Withdraw a commit

As a committer, I want to take back my commit from a link in my email, so that I can change my mind without fuss.

The withdraw page (R10) and the withdraw POST (R11) use the commit's withdraw token. The GET only shows a confirm page, so email link scanners can't withdraw anyone. Withdrawing lowers the count, never undoes a confirmed plan (FR017), and sends no signal. The creator can't withdraw. The withdraw link itself appears in the committer emails from Epic 3.

Prerequisites: Story 2.2

Acceptance criteria:
- Given Mia's commit to the example plan, when `GET /w/<withdrawToken>` is requested, then it shows "Withdraw from Coffee at Blue Bottle on Sat 14 Nov?" with a **Withdraw** button, carries `noindex`, and changes nothing.
- Given Mia's withdraw page, when **Withdraw** is submitted, then the response is 303 to `/w/<withdrawToken>?done=1`, the page reads "You're out. You've withdrawn from Coffee on Sat 14 Nov. No more emails about it.", the count drops by one, and a `commit.withdrawn` event is recorded with the new active count.
- Given a confirmed plan at exactly its minimum, when a committer withdraws, then the plan stays confirmed.
- Given Mia has already withdrawn, when **Withdraw** is submitted again, then nothing is written and the response redirects to the done page.
- Given Mia has withdrawn, when she commits again with the same email, then the commit is active again with `change: "rejoined"`, the count rises by one, and her withdraw page shows the confirm view again.
- Given Mia rejoins a confirmed plan before its gathering, when she commits, then `planWorkflows.signal` is called with `committed` and her commit's ID.
- Given the creator's withdraw token, when `GET` or `POST /w/<token>` is requested, then it answers 404 with the not-found page.
- Given a plan whose gathering has started, when its withdraw page is requested, then it reads "This one has already started." with no button, and a POST writes nothing.
- Given a malformed withdraw token, when `GET /w/<token>` is requested, then it answers 404 without a database query.

## Epic 3: Confirm, remind and call off

Plans confirm or get called off on their own and through the manage link, with the right emails at the right times, each sent once. It covers FR019–FR026, NFR007 and NFR008.

### Story 3.1 (v1): Call off a plan that misses its minimum

As a committer, I want a plan that didn't reach its minimum to be dropped quietly, so that nobody turns up to an empty room.

`planWorkflow` gets its open phase: it waits with `condition(() => confirmed || calledOff, deadline − now)` and, on timeout, calls the `resolveDeadline` activity, which moves an open plan to called off only if the count is below the minimum, then returns the plan's real state. The called-off path sends `not_this_time` to every active committer through `sendToCommitters`, then ends. Activities come from `createActivities({ db, sendEmail })`, re-read Postgres, and send through `sendOnce`. Activity options follow the architecture's Implementation Guide: `startToCloseTimeout` 30s, `scheduleToCloseTimeout` 12h, and retry from 5s with backoff 2 up to 10m. Workflow code imports only `@temporalio/workflow` and types. Every email to a committer other than the creator carries a "Can't make it? Withdraw" link (FR016). Tests use the time-skipping test environment.

Prerequisites: Story 1.5, 2.3

Acceptance criteria:
- Given the example plan with 2 active commits, when its workflow reaches the commit deadline, then the plan is called off with reason `deadline`, a `plan.called_off` event is recorded with `reason: "deadline"`, `wasConfirmed: false` and `activeCount: 2`, and each active committer gets one email with subject "Not this time: Coffee on Sat 14 Nov".
- Given a "not this time" email, when its text is read, then it says "This one didn't come together, and that's fine. Nobody's going, so there's nothing to do.", names no one and gives no count, and carries a withdraw link `BASE_URL/w/<withdrawToken>` for every committer except the creator.
- Given a committer who withdrew before the deadline, when the plan is called off, then they get no email.
- Given a plan that reached its minimum but whose `confirmed` signal never arrived, when its workflow reaches the deadline, then `resolveDeadline` leaves it confirmed and no "not this time" email is sent.
- Given the first send of a "not this time" email fails, when the activity is retried, then each committer still gets exactly one email.
- Given a called-off plan, when its public page is requested, then it shows "Not this time" with no form, and `og:description` reads "Not this time".
- Given a called-off plan, when someone commits, then the response redirects with `notice=closed` and nothing is stored.
- Given a called-off plan, when a committer's withdraw page is requested, then it reads "This one isn't going ahead, so there's nothing to withdraw from." with no button.

### Story 3.2 (v1): Confirmation emails

As a committer, I want an email the moment the plan is on, so that I know to keep the time free.

On the `confirmed` signal, or when `resolveDeadline` finds the plan confirmed, the workflow sends `confirmed` to every active committer. While confirmed, a `committed(commitId)` signal sends `confirmed` to that one committer straight away (FR019). Each committer gets it at most once, even if they withdraw and rejoin (the ledger keys on commit and kind).

Prerequisites: Story 3.1

Acceptance criteria:
- Given the example plan with Ana, Mia and Raj in, when it's confirmed, then each of them gets one email with subject "It's on: Coffee at Blue Bottle, Sat 14 Nov 10:00 AM", listing "Ana, Mia, Raj", the venue, the time and a map link for "Blue Bottle Oakland".
- Given a confirmed plan, when Lee commits before the gathering, then Lee gets the confirmation email straight away and nobody else gets a second one.
- Given a plan confirmed by a commit whose signal failed, when its workflow reaches the deadline, then every active committer gets the confirmation email then.
- Given the `confirmed` signal arrives twice, when the workflow handles it, then each committer still gets one confirmation email.
- Given a committer who withdrew before the plan was confirmed, when it's confirmed, then they get no confirmation email.
- Given Mia got the confirmation email, withdrew and rejoined, when her rejoin is signalled, then she isn't emailed again.

### Story 3.3 (v1): Reminders before the gathering

As a committer, I want reminders the day before and the morning of, so that I actually show up.

While confirmed, the workflow waits on timers for the 24h reminder and the morning reminder from the schedule, skipping any whose time has passed. It records when the 24h reminder actually went out, and skips the morning one if that was less than 6h before it (FR020, FR021). Each reminder goes to the active committers at that moment.

Prerequisites: Story 3.2

Acceptance criteria:
- Given the example plan confirmed before Fri 13 Nov, when its workflow runs, then each active committer gets "Tomorrow: Coffee at Blue Bottle, 10:00 AM" at `2026-11-13T18:00:00Z` and "Today: Coffee at Blue Bottle, 10:00 AM" at `2026-11-14T16:00:00Z`.
- Given a confirmed plan for 09:30 on 2026-11-14, when its workflow runs, then only the 24h reminder is sent.
- Given the example plan published with Decide by Sat 14 Nov 2026 6:00 AM and confirmed at Fri 13 Nov 2026 8:00 PM, when its workflow runs, then the 24h reminder is skipped and the morning reminder is sent at `2026-11-14T16:00:00Z`.
- Given a committer who joins a confirmed plan after its 24h reminder went out, when the workflow runs, then they get the confirmation email and the morning reminder, and no 24h reminder.
- Given the example plan's 24h reminder send fails until Sat 14 Nov 2026 3:00 AM and then succeeds, when 08:00 comes, then the morning reminder is skipped.
- Given a committer who withdraws after the 24h reminder, when the morning reminder goes out, then they don't get it.
- Given a confirmed plan for Sun 1 Nov 2026 at 10:00, when its workflow runs, then the 24h reminder goes at `2026-10-31T18:00:00Z` and the morning reminder at `2026-11-01T16:00:00Z`.

### Story 3.4 (v1): See the plan on the manage page

As a creator, I want my manage link to show who's in and what I can do, so that I can follow my plan.

The manage page is the API specification's R7: state pill, count against the minimum, committers' full names (never emails), the public link with **Copy**, and the actions. **Call it off** is a quiet `<details>` with the inline confirm. Its POST is Story 3.5.

Prerequisites: Story 2.3

Acceptance criteria:
- Given the example plan with Ana and Mia Chen in, when `GET /m/<manageToken>` is requested, then it shows the pill "Needs 1 more · decide by Wed 11 Nov, 10:00 PM", "2 of 3", the names "Ana Ruiz" and "Mia Chen", the public link `BASE_URL/p/<publicToken>`, a "Call it off" control, and a "Start a new plan from this" link to `/m/<manageToken>/new`.
- Given the "Call it off" control is opened, when its content is read, then it says "Call it off? Everyone who's in gets a short "not this time" email." with a **Keep it** link to `/m/<manageToken>` and a **Call it off** form that posts to `/m/<manageToken>/call-off`.
- Given a called-off plan, when its manage page is requested, then the pill reads "Not this time", the names are a plain list, there's no "Call it off", and "Start a new plan from this" is the primary action.
- Given a confirmed plan whose gathering has started, when its manage page is requested, then there's no "Call it off".
- Given any plan, when its manage page is rendered, then no email address appears in the HTML and the response carries `noindex`.
- Given a manage token that matches no plan, or a malformed one, when `GET /m/<token>` is requested, then it answers 404, and the malformed one doesn't query the database.

### Story 3.5 (v1): Call a plan off through the manage link

As a creator, I want to call my plan off, even once it's on, so that nobody turns up if plans change.

`POST /m/:token/call-off` (R8) calls the plan off with reason `creator` under the row lock, then signals `calledOff`. On that signal the workflow sends `not_this_time` to the active committers and ends, so no reminder or check-in follows (FR023, FR024).

Prerequisites: Story 3.3, 3.4

Acceptance criteria:
- Given an open plan, when the creator calls it off, then the response is 303 to `/m/<manageToken>`, the plan is called off with reason `creator`, a `plan.called_off` event is recorded with `wasConfirmed: false`, and `planWorkflows.signal` is called with `calledOff`.
- Given a confirmed plan whose confirmation emails went out, when the creator calls it off before the gathering, then the event records `wasConfirmed: true`, every active committer gets the "Not this time" email once, and no reminder or check-in is sent afterwards.
- Given a called-off plan, when the call-off is posted again, then nothing is written and the response redirects to `/m/<manageToken>`.
- Given a plan whose gathering has started, when the call-off is posted, then nothing is written and the response redirects to `/m/<manageToken>?notice=too-late`, which shows "It's already started, so it can't be called off.".
- Given `planWorkflows.signal` fails, when the creator calls the plan off, then the plan is still called off, the response is the usual 303, and the failure is logged at `error`.
- Given a call-off POST that fails the CSRF check, when it's sent, then the response is 403 and the plan isn't called off.

### Story 3.6 (v1): Start a new plan from an old one

As a creator, I want to start a new plan from my old one with a new date, so that retrying takes seconds.

`GET /m/:token/new` (R9) renders the create page in the suggestion-card shape, without **Suggest another** or **Change**, pre-filled from the old plan. Publishing goes through `POST /plans` with `fromManageToken`. The new plan gets new tokens and a new workflow, the creator is its only committer, and the old committers aren't emailed (FR025).

Prerequisites: Story 1.8, 3.4

Acceptance criteria:
- Given a called-off example plan, when `GET /m/<manageToken>/new` is requested, then the card shows "Coffee", "Blue Bottle" and minimum 3, the summary "Oakland · Rockridge · next weekend, morning" read-only, date and time empty and editable, Decide by empty, Ana's name and email filled in, and no **Suggest another** or **Change**.
- Given that form with the date 2026-11-21 and time 10:00, when it's published, then a new plan is stored with new tokens, `from_plan_id` set to the old plan, a `plan.published` event with `fromPlanId`, Ana as its only committer, the old plan unchanged, and `planWorkflows.start` called for the new plan.
- Given the new plan is published, when the emails are read, then Ana gets one manage-link email for the new plan and none of the old plan's committers is emailed.
- Given an open, confirmed or called-off plan, when its new-plan page is requested, then it renders.
- Given a `fromManageToken` that matches no plan, when the form is published, then the plan is published with no `from_plan_id`.
- Given both `suggestionId` and a valid `fromManageToken`, when the form is published, then `from_plan_id` is set and `suggestion_id` is null.
- Given that form with no date, when it's published, then the response is 422 with the new-plan page re-rendered, "Pick a date." shown, and the pre-filled values kept.

## Epic 4: Check-in and trial data

The operator can measure the success test from the stored data and the creator's check-in answers, and calvin runs in production for the 3–5 trials. It covers FR027–FR029 and NFR010.

### Story 4.1 (v1): Send the check-in

As the operator, I want the creator of a confirmed plan asked whether it happened, so that I can measure the success test.

After the reminders, the workflow waits until the schedule's check-in time (10:00 the day after the gathering) and sends `check_in` to the creator only, through `sendOnce`, then ends. A plan called off at any point gets no check-in (FR027).

Prerequisites: Story 3.5

Acceptance criteria:
- Given the example plan confirmed, when its workflow reaches `2026-11-15T18:00:00Z`, then Ana gets one email with subject "Did it happen? Coffee on Sat 14 Nov", asking "Did it happen?" and "Were you there?" with the links `BASE_URL/c/<checkInToken>/happened/yes`, `…/happened/no`, `…/attended/yes` and `…/attended/no`.
- Given the example plan confirmed, when the check-in is sent, then no other committer gets it, and the workflow ends.
- Given a plan called off by its deadline, or by its creator before or after confirmation, when its check-in time would have come, then no check-in is sent.
- Given a confirmed plan for Sun 1 Nov 2026 at 10:00, when its workflow runs, then the check-in is sent at `2026-11-02T18:00:00Z`.

### Story 4.2 (v1): Answer the check-in

As a creator, I want to answer the check-in with one tap per question, so that it takes no effort.

`GET /c/:token/:question/:answer` (R12) records the answer on open. Answering again replaces the earlier answer (FR028). The GET writes on purpose: a link prefetch at worst records a default the creator can correct.

Prerequisites: Story 4.1

Acceptance criteria:
- Given a confirmed plan with no answers, when `GET /c/<checkInToken>/happened/yes` is requested, then it answers 200 with "Thanks! Got it: it happened.", the answer is stored, a `check_in.answered` event is recorded, and the page asks "Were you there?" with Yes and No links to `/c/<checkInToken>/attended/yes` and `…/attended/no`.
- Given "happened" was answered yes, when `GET /c/<checkInToken>/happened/no` is requested, then the stored answer becomes no and the page reads "Thanks! Got it: it didn't happen.".
- Given both questions are answered, when `GET /c/<checkInToken>/attended/no` is requested, then the page reads "Thanks! Got it: you weren't there." and asks nothing more.
- Given an open or called-off plan, when its check-in link is requested, then it answers 404 with the not-found page and nothing is stored.
- Given a question other than `happened` or `attended`, or an answer other than `yes` or `no`, when the link is requested, then it answers 404.
- Given a malformed check-in token, when the link is requested, then it answers 404 without a database query.
- Given any check-in page, when its headers are read, then it carries `noindex`.

### Story 4.3 (v1): Deploy calvin for the trial

As the operator, I want calvin running on one Fly.io machine with its real services, so that the 3–5 trials can start.

Hosting follows ADR 0003 and the architecture's Fly.io configuration: one Machine in `sjc`, `shared-cpu-1x` with 512MB, autostop off, one machine always running, HTTPS forced, a health check on `GET /healthz`, a release command that runs the migrations, and a `node:26-slim` image installing with `npm ci --omit=dev` and running the entry point. Secrets are set with `fly secrets set` only. An example env file lists every variable's name and no values. The operator's own steps, listed in the plan: choose the domain, verify the `send.` subdomain in Resend (SPF, DKIM and a `_dmarc` record with `p=none`), create the Temporal Cloud namespace and its API key, and create the Neon project in `aws-us-west-2`. Everything in this story is checked by hand.

Prerequisites: Story 4.2

Acceptance criteria:
- Given the container image built from the repo, when it's started with the environment variables set, then `GET /healthz` answers `ok` (checked by hand).
- Given a deploy, when it runs, then the release command applies the migrations to the Neon database before the new machine starts, and a failing migration stops the deploy (checked by hand).
- Given the repo, when it's scanned, then no secret value appears in the Fly config, the container definition or the example env file, and `gitleaks git --redact --exit-code 1` passes.
- Given production, when a plan is created from a real suggestion and published, then the manage-link email arrives in the inbox with SPF and DKIM passing, and the plan's workflow `plan-<planId>` is running in the Temporal Cloud namespace (checked by hand).
- Given a test plan taken through commit, confirmation and call-off in production, when the operator runs the database schema's trial metric queries, then they return its share, outcome and suggestion figures (checked by hand).
- Given a month of the Fly, Neon, Temporal Cloud, Resend and Anthropic plans in use, when the costs are added up, then the estimate is under $20 (checked by hand).
